Serviço de Pagamento

Responsável por validar requisições, verificar saldo, garantir idempotência, persistir o estado do pagamento e integrar o resultado aos demais serviços do PZaaS.

HTTP / JSON n8n Redis Serviço 04
Nota de segurança: a chave x-api-key exibida nesta documentação é a chave utilizada no ambiente acadêmico de testes. Não utilize credenciais reais em documentação pública.
01

Visão geral

O Serviço 04 é responsável pelo pagamento no PZaaS. Ele recebe os dados do pedido, valida a requisição, verifica se o saldo informado é suficiente e registra o resultado como aprovado ou recusado.

O fluxo principal foi desenvolvido no n8n usando Webhook, IF, Edit Fields, Redis, HTTP Request e Respond to Webhook. O Health Check fica junto do serviço de Pagamento. A integração usada nos testes com o Chaos Monkey foi deixada em um workflow separado, para não misturar o fluxo normal com a simulação de falhas.

03

Entrada do pagamento

A rota principal recebe uma requisição POST em /v1/turmaa21_Pagamento/fluxo. O body contém o identificador do pedido, o cliente, o valor da compra e o saldo disponível informado na requisição.

Body de exemplo

{
  "pedido_id": "8030",
  "cliente": "Joao",
  "valor": 79.90,
  "saldo_cliente": 100.00
}

Headers utilizados

Content-Type: application/json
x-api-key: turma2026
x-pedido-id: 8030
04

Processamento do pagamento

O processamento segue esta ordem: validação da API Key, validação do x-pedido-id, consulta no Redis para evitar cobrança duplicada e verificação do saldo.

4.1 Validação da API Key

O header x-api-key é comparado com a chave configurada no workflow (turma2026). Se estiver ausente ou incorreto, o fluxo é encerrado com resposta 401.

{
  "erro": "API_KEY_INVALIDA",
  "mensagem": "Acesso não autorizado."
}

4.2 Validação do x-pedido-id

Depois da API Key, o serviço verifica se o header x-pedido-id foi enviado. Se estiver ausente, a requisição é rejeitada com código 400.

{
  "erro": "PAYLOAD_INVALIDO",
  "mensagem": "Dados obrigatórios do pagamento estão ausentes ou inválidos."
}

4.3 Verificação de pagamento já processado

Com os headers validados, o fluxo consulta o Redis usando uma chave no formato:

pedido:<pedido_id>

Exemplo:

pedido:8030

Se o pedido já estiver salvo como APROVADO, ele não é processado novamente. Isso evita que uma repetição da mesma chamada gere uma nova cobrança.

{
  "pedido_id": "8030",
  "status": "APROVADO",
  "motivo": "PAGAMENTO_JA_PROCESSADO"
}

4.4 Verificação do saldo

Se o pedido ainda não estiver aprovado, o fluxo compara o saldo informado com o valor da compra:

saldo_cliente >= valor

Quando a condição é verdadeira, o fluxo segue para aprovação. Caso contrário, o pagamento é recusado por saldo insuficiente. No fluxo atual, saldo_cliente é usado para a decisão do pagamento; o saldo do cliente não é mantido como uma conta separada no Redis.

05

Pagamento recusado

Quando o saldo é menor que o valor da compra, o pagamento recebe status RECUSADO. O motivo usado é SALDO_INSUFICIENTE e gateway_utilizado fica como NENHUM.

{
  "pedido_id": "8031",
  "status": "RECUSADO",
  "motivo": "SALDO_INSUFICIENTE",
  "gateway_utilizado": "NENHUM"
}

O resultado é salvo no Redis e enviado ao Logger. Essa situação é tratada como recusa de negócio, não como erro técnico do serviço.

06

Pagamento aprovado

Quando o saldo é suficiente, o pedido passa pelo estado PENDENTE e depois é atualizado para APROVADO. No caminho principal, o campo gateway_utilizado recebe PRINCIPAL.

{
  "pedido_id": "8030",
  "status": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null
}
Por que motivo é null? Porque não existe motivo de recusa em um pagamento aprovado. O estado final também é persistido no Redis.
07

Uso do Redis

O Redis é usado para guardar o estado do pagamento e para a verificação de idempotência. A chave é baseada no pedido_id e o valor armazenado contém os dados principais da operação.

Pagamento aprovado

{
  "cliente": "Joao",
  "valor": 79.90,
  "status": "APROVADO",
  "gateway_utilizado": "PRINCIPAL"
}

Pagamento recusado

{
  "cliente": "Joao",
  "valor": 79.90,
  "status": "RECUSADO",
  "motivo": "SALDO_INSUFICIENTE",
  "gateway_utilizado": "NENHUM"
}
08

Logger

O serviço envia logs dos pagamentos aprovados e recusados para o Logger. A chamada possui retry e foi configurada para não interromper o pagamento caso o Logger esteja indisponível.

{
  "servico": "pagamento",
  "pedido_id": "8030",
  "status": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null
}
09

Comunicação com o Orquestrador

No protótipo atual, após a aprovação o workflow envia o resultado para o Orquestrador. As URLs usadas durante o desenvolvimento podem ser provisórias e devem ser substituídas pelos endpoints combinados entre as duplas na integração final.

{
  "pedido_id": "8030",
  "cliente": "Joao",
  "valor": 79.90,
  "status_pagamento": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null,
  "servico_origem": "pagamento"
}

Headers enviados

Content-Type: application/json
x-api-key: turma2026
x-pedido-id: 8030
Essa chamada de retorno deve permanecer somente se fizer parte do contrato final definido com a dupla do Orquestrador.

9.1 Fallback do Orquestrador

No fluxo implementado, a chamada tenta primeiro o Orquestrador A. Em caso de falha, a saída de erro segue para o Orquestrador B. Se os dois estiverem indisponíveis, a resposta final é 503.

10

Health Check

O Health Check verifica se o serviço consegue acessar o Redis. O endpoint faz uma leitura da chave health:pagamento. Se a operação funcionar, retorna 200; se houver erro de conexão com o Redis, retorna 503.

GET/v1/turmaa21/health

Redis disponível · 200

{
  "service": "pagamento",
  "status": "UP",
  "version": "v1",
  "dependencies": {
    "redis": "UP"
  }
}

Redis indisponível · 503

{
  "service": "pagamento",
  "status": "DEGRADED",
  "version": "v1",
  "dependencies": {
    "redis": "DOWN"
  }
}
11

Integração com o Chaos Monkey

O Chaos Monkey é o Serviço 10 e pertence a outra dupla. Para permitir os testes de falha no Pagamento, foi criado um workflow separado com um Webhook que pode ser chamado por essa dupla. Esse workflow não implementa o Chaos Monkey; ele apenas recebe a solicitação de teste e devolve a falha configurada.

POST/v1/turmaa21_pagamento/chaos_monkey

Body recebido

{
  "pedido_id": "8030",
  "tipo_falha": 500
}

tipo_falha = 500

{
  "servico": "pagamento",
  "pedido_id": "8030",
  "erro": "FALHA_SIMULADA",
  "tipo_falha": 500
}

tipo_falha = 503

{
  "servico": "pagamento",
  "pedido_id": "8030",
  "erro": "FALHA_SIMULADA",
  "tipo_falha": 503
}

Outros valores

{
  "servico": "pagamento",
  "pedido_id": "8030",
  "status": "OK",
  "chaos": false
}

14

Integração com os outros serviços

O Pagamento faz parte do fluxo maior do PZaaS. O pedido passa pelo Gateway e pelo Orquestrador, que coordena as dependências do checkout. O serviço de Pagamento recebe os dados necessários para decidir a operação e devolve o resultado.

Cliente→API Gateway→Orquestrador→Pagamento

O Cadastro/Identidade participa da arquitetura validando token e perfil, mas não foi colocado como uma chamada direta do Pagamento.

15

Estado atual da implementação

O fluxo principal já possui validação de headers, consulta ao Redis, idempotência para pedidos aprovados, verificação de saldo, aprovação, recusa por saldo insuficiente, Health Check, envio de logs e tratamento de fallback nas integrações configuradas.

A integração com o Chaos Monkey está separada do workflow principal e serve apenas para os testes controlados com a dupla responsável pelo Serviço 10.

Antes da entrega final: ainda é necessário confirmar as URLs definitivas dos outros serviços e validar o contrato final de comunicação com o Orquestrador.

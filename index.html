1. Visão geral

Nosso serviço é o Pagamento - Serviço 04. Ele recebe os dados de um pedido, valida os headers, verifica no Redis se o pedido já foi processado e compara o saldo do cliente com o valor da compra.

Quando o saldo é suficiente, o pedido segue como aprovado. Quando não é suficiente, ele é recusado. Também usamos Redis para guardar o estado do pagamento, Logger para registrar as operações, Orquestrador para continuar o fluxo e um Health Check para verificar a disponibilidade do Redis.

POST https://pzaas.online/webhook/v1/turmaa21_pagamento/chaos_monkey

Ativa ou desativa a falha controlada do serviço de Pagamento.

3. Pagamento

Entrada

O fluxo principal recebe uma requisição POST com os dados abaixo:

{
  "pedido_id": "ped-0337",
  "cliente_id": "cli-0001",
  "itens": [
    {
      "pizza_id": "calabresa",
      "qtd": 1
    }
  ],
  "valor": 79.90,
  "saldo_cliente": 100.00
}

Headers usados

Content-Type: application/json
x-api-key: turma2026
x-pedido-id: ped-0337

Contrato atual do pedido

O pagamento trabalha com o identificador do pedido, o cliente_id, a lista de itens solicitados, o valor total e o saldo informado. O nome do cliente não é necessário neste serviço.

pedido_id   → identifica o pedido
cliente_id  → identifica o cliente
itens       → pizzas e quantidades solicitadas
valor       → total da compra
saldo_cliente → saldo usado na validação do pagamento

Validações

Primeiro o serviço consulta o estado do Chaos Monkey. Se o serviço não estiver em falha, ele continua para a validação da API Key e depois verifica se o x-pedido-id foi enviado.

Depois disso, consulta a chave pedido:<pedido_id> no Redis. Se o pedido já estiver salvo como APROVADO, ele não é processado de novo.

Saldo

saldo_cliente >= valor

Se a condição for verdadeira, o pagamento passa por PENDENTE e termina como APROVADO. Caso contrário, fica como RECUSADO por saldo insuficiente.

Exemplo aprovado

{
  "pedido_id": "ped-0337",
  "status": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null
}

Exemplo recusado

{
  "pedido_id": "ped-0338",
  "status": "RECUSADO",
  "motivo": "SALDO_INSUFICIENTE",
  "gateway_utilizado": "NENHUM"
}

4. Redis

O Redis é usado em duas partes importantes do projeto: para salvar o estado do pagamento e para controlar a falha do Chaos Monkey.

Estado do pedido

pedido:8030

Nessa chave ficam as informações do pagamento, como cliente_id, itens do pedido, valor, status e gateway utilizado.

Controle do Chaos

chaos:pagamento = 503

Quando essa chave existe com valor 503, o fluxo principal entende que o serviço está indisponível e retorna erro antes de processar o pagamento.

5. Logger

Depois do resultado do pagamento, enviamos um log para o serviço de Logger. Existem chamadas para pagamento aprovado e para saldo insuficiente.

A chamada de Logger está configurada com retry e para continuar o fluxo mesmo se houver erro nessa integração, evitando que uma falha no log impeça o pagamento de terminar.

{
  "servico": "pagamento",
  "pedido_id": "ped-0337",
  "cliente_id": "cli-0001",
  "status": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null
}

6. Orquestrador e fallback

Quando o pagamento é aprovado, o resultado é enviado para o Orquestrador A. Se essa chamada falhar, o workflow tenta o Orquestrador B.

Pagamento aprovado→Logger→Orquestrador A→Fallback B

Payload enviado ao Orquestrador

O resultado aprovado é repassado mantendo o cliente_id e os itens recebidos no pedido.

{
  "pedido_id": "ped-0337",
  "cliente_id": "cli-0001",
  "itens": [
    {
      "pizza_id": "calabresa",
      "qtd": 1
    }
  ],
  "valor": 79.90,
  "status_pagamento": "APROVADO",
  "gateway_utilizado": "PRINCIPAL",
  "motivo": null,
  "servico_origem": "pagamento"
}

Se os dois estiverem indisponíveis, o serviço devolve um erro de indisponibilidade relacionado ao Orquestrador.

{
  "erro": "SERVICO_INDISPONIVEL",
  "mensagem": "Orquestrador indisponivel apos fallback",
  "dependencia": "orquestrador",
  "servico": "pagamento"
}

7. Health Check

O endpoint de Health Check faz uma consulta no Redis usando a chave health:pagamento.

Se não houver erro na operação, retorna o serviço como UP e o Redis como UP. Se houver erro, o retorno fica como DEGRADED e Redis DOWN.

{
  "service": "pagamento",
  "status": "UP",
  "version": "v1",
  "dependencies": { "redis": "UP" }
}
{
  "service": "pagamento",
  "status": "DEGRADED",
  "version": "v1",
  "dependencies": { "redis": "DOWN" }
}

8. Chaos Monkey

O Chaos Monkey agora interfere no fluxo principal de verdade. A ideia foi usar uma chave no Redis para indicar quando o serviço de Pagamento deve ficar indisponível.

Ativar a falha

Chamamos o endpoint de Chaos com:

{
  "tipo_falha": 503
}

O workflow verifica se tipo_falha é igual a 503. Se for, executa:

SET chaos:pagamento = 503

Depois disso, qualquer nova chamada no endpoint principal de Pagamento consulta essa chave logo no início. Se encontrar 503, o pagamento não continua.

{
  "erro": "SERVICO_INDISPONIVEL",
  "servico": "pagamento",
  "motivo": "CHAOS_MONKEY",
  "mensagem": "Servico de pagamento indisponivel."
}

Desativar a falha

Para normalizar o serviço, enviamos outro valor, como:

{
  "tipo_falha": 0
}

Como não é 503, o outro caminho do IF executa:

DELETE chaos:pagamento

A chave é removida e as próximas chamadas de pagamento voltam a seguir o fluxo normal.

Teste que usamos no Postman: 503 → ativa o Chaos → pagamento fica indisponível 0 → remove a chave → pagamento volta ao normal
